# 테크노관 실내 길찾기 설계

작성일: 2026-08-26

## 목적

테크노관(61번 건물) B1F~6F 내부에서, 사용자가 지정한 출발 지점부터
목적지 방의 **문**까지 가는 최적 경로를 계산한다. 이동 수단은 복도 보행,
계단, 엘리베이터. 거리는 층별 도면 축척으로 실제 미터를 산출한다.

## 입력 데이터

`GUMAP-개발/floorplan/work/{층}_labeled.json` (도면 픽셀 좌표)

| type | 개수 | 쓰임 |
|---|---|---|
| `corridor` | 층당 1개 (구멍 포함 폴리곤) | 보행 가능 영역 |
| `door` | 449개 (전부 `connects` 보유) | 방/계단/EV ↔ 복도 접속 |
| `stairs` | 33개 (`connects_floors`) | 층간 이동 |
| `elevator` | 20개 (`connects_floors`) | 층간 이동 |
| `room` | 338개 | 목적지, 출발점 포함 판정 |

축척: `techno_georef.json` 의 `floor_px_per_mm[층]`, 좌표변환: `transform`.

### 확인된 데이터 사실

- 문 박스 중심은 복도 폴리곤 **바깥** 중앙값 4px(≈0.16m) — 벽 위에 그려져 있다.
  따라서 문 노드는 복도 안으로 투영한 **진입점**을 따로 만든다.
- 계단/EV 박스는 복도에서 23~108px(1~4.5m) 떨어져 있고 전용 문으로만 닿는다.
- 층간 연결 선언은 (3F 계단-A 오타 수정 후) **완전 대칭**이며 실제 건물과 일치한다.
  4F 계단-D/E 가 5F 로 안 가는 것은 데이터 오류가 아니라 사실이다.
- 문이 없는 방 26개(B1F 3·1F 1·2F 14·3F 7·5F 1)는 이번 범위 밖.
  경로 요청 시 방 경계 → 복도 최근접 투영점을 `추정 진입점`으로 쓰고 경고를 붙인다.

## 그래프 모델 — 가시성 그래프(visibility graph)

격자 A*(무겁고 계단현상) 와 중심선 스켈레톤(경로가 길어짐) 대신 가시성 그래프를
쓴다. 복도 폴리곤이 이미 직사각형 위주로 단순화돼 있어(꼭짓점 44~82개) 그래프가
작고, 최단경로가 근사가 아니라 **기하학적으로 정확**하다. 순수 기하 연산이라
Python 과 JS 가 같은 답을 낸다.

### 노드

| 종류 | 좌표 | 비고 |
|---|---|---|
| `corridor` | 복도 폴리곤 반사각 꼭짓점을 안쪽으로 민 점 | 코너 우회용 |
| `door` | 문 박스 정중앙 | 목적지 표시 좌표 |
| `door_access` | 문 중앙에서 복도 안쪽으로 투영·inset 한 점 | 그래프 접속점 |
| `stair` / `elevator` | 박스 중심 | 층간 엣지의 끝점 |
| `room` | 방 중심 (출발점 판정용, 요청 시 동적 생성) | |

복도 폴리곤은 안쪽으로 **0.4m inset** 해서 경로가 벽에 붙지 않게 한다.

### 엣지

- **수평**: 같은 층 노드쌍 중 inset 복도 폴리곤 안에서 line-of-sight 가 통하는 쌍.
  가중치 = 픽셀거리 ÷ `floor_px_per_mm[층]` ÷ 1000 (미터).
- **문 ↔ 진입점**: 짧은 고정 엣지.
- **계단/EV ↔ 복도**: 해당 `door` 를 통해서만.
- **수직**: 같은 이름(계단-A, EV-1)의 노드를, **양쪽 층이 서로를 선언한 경우에만** 연결.

## 비용과 거리

경로 탐색 비용은 **시간(초)**, 결과에는 거리(m) 와 시간을 함께 싣는다.

| 항목 | 값 |
|---|---|
| 보행 속도 | 1.2 m/s |
| 계단 | 층당 20초 (수직 4.0m) |
| 엘리베이터 | 대기 25초 + 층당 6초 |

옵션 `avoid_stairs=true` (배리어프리) → 계단 엣지 제외.

## 질의 인터페이스

```
route(start={floor, x, y}, dest={room_id, floor?}, options={avoid_stairs})
  → {
      ok, distance_m, duration_s,
      legs: [{floor, mode: walk|stairs|elevator, points_px, points_lonlat, distance_m}],
      destination: {room_id, floor, door_center_px, door_center_lonlat},
      steps: ["직진 12m", "계단-B 에서 3층으로", ...],
      warnings: []
    }
```

- 출발점이 복도 안 → 바로 가시성 접속.
- 출발점이 방 안 → 그 방의 문(들)을 경유.
- 둘 다 아님 → 최근접 복도점으로 스냅하고 경고.
- 목적지 방에 문이 여러 개면 **총비용 최소인 문**을 고른다.

## 코드 구성

```

05_build_nav.py            work/techno_nav.json + 프론트 번들 생성
floorplan-editor.html      "길찾기" 모드 (테스트 표면)

```

`fp/nav.py` 는 픽셀 좌표만 다루고 lon/lat 을 모른다. 좌표변환은 기존 `fp/georef.py`
가 유일한 창구라는 규칙을 그대로 지킨다.

## 검증

`GUMAP-개발/floorplan/tests/test_nav.py`

1. 축척 — 알려진 픽셀 거리 → 미터 환산이 도면 치수와 맞는지
2. 연결성 — 문이 있는 모든 방이 1F 출입구에서 도달 가능한지
3. **경로가 방 내부를 관통하지 않는지** (경로 폴리라인 ∩ 방 폴리곤)
4. 층간 경로가 실제로 계단/EV 노드를 경유하는지
5. `avoid_stairs` 가 계단 엣지를 쓰지 않는지
6. 삼각부등식 스모크 (A→C ≤ A→B→C)

## 구현 결과 (2026-08-27)

설계에서 바뀐 점과 구현하며 알게 된 것.

### 데이터 수정 3건

| 위치 | 증상 | 조치 |
|---|---|---|
| 3F 계단-A `connects_floors` | `["2F. 4F"]` (쉼표가 마침표) | `["2F","4F"]` 로 수정 |
| 1F 문 2개 `connects` | `["복도. 계단-C", ""]` 같은 형태 | 갈라서 수정 |
| — | 같은 오타가 다시 들어와도 안 깨지게 | `nav.normalize_tokens()` 가 읽는 시점에 정규화하고 경고를 남긴다 |

오타 수정 후 층간 연결 선언은 **완전 대칭**이 됐다. 그래서 층간 엣지 규칙을
"양쪽이 서로 선언한 경우에만" 으로 확정했다. "인접층에 같은 이름이 있으면 잇는다"
같은 추측 규칙은 쓰지 않는다 — 4F 계단-D·E 가 5F 로 가지 않는 것은 실제 건물이
그렇기 때문이다.

### 설계에서 바꾼 것 2가지

**① 추정 진입점을 그래프에 미리 굽는다.**
복도와 닿는 문이 하나도 없는 방이 31개 있다 (문 박스 자체가 없는 26개 + 옆방을
통해서만 들어가는 5개). 이걸 조회 시점에 처리하면 파이썬과 브라우저가 각자
폴백 기하 연산을 구현해야 하고, 두 구현이 갈라진다. `nav.build()` 가 빌드 때
`entry` 노드를 만들어 그래프에 넣으므로 양쪽이 같은 답을 낸다.

**② 경로 기하를 단순화하지 않는다.**
처음에는 "거의 일직선(12° 이내)인 중간점 제거" 를 넣었다. 마지막으로 남긴 점을
기준으로 각도를 재는 방식이라 긴 구간에서 오차가 누적됐고, **무작위 600회 중
4회에서 경로선이 복도를 벗어나 옆방을 최대 2m 가로질렀다**. 가시성 그래프의
경로는 이미 반사각 꼭짓점에서만 꺾이므로 지울 중간점이 없다. 지금은 겹치는
점만 뺀다. 완만한 굽이를 "직진" 으로 묶는 일은 안내문 생성에서만 하고 선은
건드리지 않는다.

## 부록 · map-layers.js 복구 (2026-08-27)

길찾기 검증 중 발견한 별건. 요청을 받아 함께 복구했다.

### 증상

커밋 4fdee1f 에서 `GUMAP-프론트/js/map/map-layers.js` 가 **UTF-8 → cp949 → UTF-8
이중 인코딩 손상**을 입었다. 한글 주석이 깨진 것에 그치지 않고,

- 줄 끝 한글의 마지막 바이트가 개행(0x0A)과 짝을 이뤄 **13줄이 앞줄에 흡수**됐다.
  그래서 `window.Ortho4326TmsLayer = L.TileLayer.extend({` 같은 선언이 주석 안으로
  들어가 버렸다.
- 문자열 리터럴의 **닫는 따옴표까지 먹혔다** (`'킥보드';` → `'?λ낫??;`).

결과적으로 파일 전체가 `SyntaxError` 로 파싱되지 않아, CCTV · 교통사고 · 공유PM ·
주유소 · 정사영상 · DEM · 실시간교통 레이어와 마커 겹침 필터가 전부 죽어 있었다.

### 복구 방법

깨진 파일은 제자리 수리가 불가능하다 (한글이 복원 불가능하게 손실됐다).
정상 커밋 2c6031f 을 바탕으로 두고, 4fdee1f 가 **의도했던 변경만** 다시 얹었다.

주석을 걷어낸 코드끼리 diff 해서 확인한 의도된 변경은 3곳뿐이었고 전부 같은 종류다:

```
- 'http://localhost:8765/...'
+ window.location.protocol + '//' + window.location.hostname + ':8765/...'
```

타일 서버(정사영상 8765, DEM 8767) 주소를 하드코딩 localhost 대신 **접속한 호스트
기준**으로 바꾼 것 — 다른 기기에서 접속해도 타일이 뜨게 하려던 변경이다.
나머지 차이는 전부 인코딩 손상이었다.

교차 확인: `GUMAP-일반지도/map/map-layers.js` 는 4fdee1f 가 건드리지 않아 온전했고,
복구본과 정확히 이 3줄만 달랐다. 833줄·한글 1,108자가 일치해 복구가 정확함을
확인했다. 같은 의도가 적용되어야 하므로 그 사본에도 3줄을 적용했다.

### 같은 커밋의 다른 사고

`server.py` 의 `MemoryCache` 도 같은 커밋에서 `get`/`set` 이 **중복 삽입**됐다.
파이썬은 뒤 정의를 쓰므로, 나중에 붙은 축출 없는 `set` 이 이겨 **2000개 캐시 상한이
죽어 있었다**(무한 증가). 중복 쌍을 지워 축출 로직이 있는 정의만 남겼다.
서버 프로세스는 재시작해야 반영된다.

## 부록 · 성능 조사 (2026-08-27)

"본서버 로딩이 오래 걸리고, 크롬을 켜면 컴퓨터 전체가 버벅인다" 는 신고를
측정으로 추적했다. 서로 무관한 원인 두 가지였다.

### 원인 ① 버벅임 — 페인트 애니메이션 2,178개

`.bus-stop-glow-marker` 가 `markerPulse` 로 **box-shadow** 를 `infinite`
애니메이션하고 있었다. box-shadow 는 GPU 합성이 불가능한 **페인트 속성**이라
요소마다 매 프레임 재래스터화가 필요하다.

그리고 [map-init.js](../../../GUMAP-프론트/js/map/map-init.js) 는 zoom 16 이상이면
구미시 정류장 **2,178개를 화면 밖까지 전부** 지도에 올렸다. 건물 하나를 보는
zoom 19 에서도 2,178개가 DOM 에 남아, **화면에 하나도 안 보이면서** 매 프레임
페인트 비용을 냈다. zoomend 마다 2,178개를 전부 addTo/remove 하기도 했다.

통제 실험(런타임 토글, 코드 미수정):

| 조건 | 프레임 중앙값 | DOM 마커 |
|---|---|---|
| 기준 | 33.3ms (30fps) | 2,247 |
| 애니메이션만 끔 | 16.7ms (60fps) | 2,247 |
| 화면 밖 마커만 제거 | 16.7ms (60fps) | 69 |
| 둘 다 | 16.7ms (60fps) | 69 |

둘 중 **하나만 고쳐도 60fps 로 회복**된다 (애니메이션이 비용이고, 컬링은 그
애니메이션 대상을 없앤다). 둘 다 고쳤다.

- `markerPulse` → `markerPulseRing`: `transform` + `opacity` 만 쓴다 (합성 전용).
  퍼지는 링은 `::after` 로 분리했다. 겉모습은 그대로다.
- `window.syncStationMarkers()`: 보이는 범위(+25% 여유)만 지도에 올린다.
  `moveend`/`zoomend` 에 붙였고, 상태가 그대로면 DOM 을 건드리지 않는다.

결과: 실내지도 표출 후 노드 11,881 → 5,347 · 마커 2,247 → 69 ·
프레임 66.6ms → 16.7ms · 롱태스크 197건 → 2건.

### 원인 ② 로딩 — localhost 의 IPv6 폴백 2초

`localhost` 는 윈도우에서 **IPv6 `::1` 로 먼저** 풀린다. 서버들이 IPv4 전용
(`0.0.0.0`, `('', port)`)으로만 듣고 있어 `::1` 연결이 거부되는데, 윈도우는 그
거부를 돌려주기까지 약 2초를 쓴다. 그 뒤에야 IPv4 로 폴백한다.

실측:

| 대상 | 연결 시간 |
|---|---|
| `::1:3000` | 2,001.8ms (거부) |
| `127.0.0.1:3000` | 1.5ms |
| HTTP `localhost:3000` | 2,016ms |
| HTTP `127.0.0.1:3000` | 12ms |

크기와 무관하게 **모든 요청이 정확히 ~2,010ms** 였다 (3.5KB CSS 든 109KB JS 든).
크롬은 IPv4/IPv6 를 동시에 시도해(Happy Eyeballs) 상당 부분 감추지만, 그래도
페이지 로드가 **1,154ms → 779ms** 로 차이 났다. 지도를 움직일 때마다 새 연결을
받는 타일 서버(8765~8767)는 영향이 더 크다.

수정: 서버를 듀얼스택으로 바인드했다 (`::` + `IPV6_V6ONLY=0`, 실패 시 IPv4 폴백).

- `server.py` → `dual_stack_socket()` + `uvicorn.Server.run(sockets=[...])`
- `GUMAP-실행/cors_server.py` → `DualStackHTTPServer`

확인: 타일 서버 `localhost` 응답 **2,016ms → 11.8ms**.

### 곁가지

- 런처의 "AI loading ~25s" 안내는 낡았다. G-Route AI(그래프 + ONNX 4개 +
  7,444노드×3프로파일 워밍업) 포함 **실측 3.1초**. 문구를 고쳤다.
- `wait_for_port` 가 1초 간격으로 보느라 서버가 떠 있어도 최대 1초를 더
  기다렸다. 0.1초 간격으로 바꿨다.

계약을 못박는다 — 건물 화면 DOM 마커 300개 이하, 페인트 유발 무한 애니메이션

## 부록 · 건물 출입구 규칙 (2026-08-28)

건물 밖에서 방까지 한 번에 안내하려면 실내 그래프가 바깥과 만나는 지점을
알아야 한다. 박스를 그리기 **전에** 규칙을 정하고, 합성 데이터로 전 구간이
동작하는 것까지 확인해 두었다.

### 규칙

문 박스의 `connects` 에 **`외부`** 를 넣으면 그 문이 건물 출입구가 된다.

```json
{
  "type": "door",
  "connects": ["복도", "외부"],
  "room_id": "정문",
  "points": [[x1,y1],[x2,y1],[x2,y2],[x1,y2]],
  "centroid": [cx, cy]
}
```

| 항목 | 내용 |
|---|---|
| 필수 | `connects` 에 `복도` 와 `외부` 가 함께 있어야 한다 |
| 층 | 어느 층이든 된다. 그 층 JSON 에 넣으면 그 층 출입구다 (경사지라 B1F·2F 출입구도 가능) |
| 이름 | `room_id` 가 출입구 이름이 된다 (`정문`, `후문`…). 비우면 방위로 자동 (`서쪽 출입구 (1F)`) |
| 표기 흔들림 | `외부` 외에 `밖` · `EXT` · `EXTERIOR` · `OUTSIDE` · `외부출입구` 도 받는다 |
| 복도와 안 닿으면 | 출입구로 등록하지 않고 경고를 남긴다 (그래프에 붙을 데가 없다) |
| `외부` 는 방이 아니다 | 목적지 목록에 `외부` 가 섞이지 않게 따로 걸러낸다 |

에디터에서는 문을 그렸을 때 닿은 공간이 복도 하나뿐이면 `복도, 외부` 를
기본값으로 제안하고, 출입구는 지도에 `🚪🌳 출입구:정문` 으로 표시한다.

### 동작

1. `nav.build` 가 그 문을 `exterior=True` 로 표시하고 `graph.entrances` 에 모은다.
2. `05_build_nav.py` 가 출입구를 **위경도까지 붙여** 번들에 싣는다
   (`entrances: [{node, floor, name, lat, lon}]`).
3. 브라우저 엔진 `route({outdoor:true, lat, lng}, …)` 가 문을 하나 고르는 게
   아니라 **출입구 전부를 출발 후보로 깔고** (`attachOutdoorStart`) 각자의 실외
   도보시간을 초기비용으로 준다. 탐색이 끝나면 경로 사슬의 뿌리가 실제로
   들어간 문이다 (`resolveEntrance`). `mode:"outdoor"` 구간이 맨 앞에 붙는다.
4. 지도에는 실외 구간이 초록 점선으로, 안내문 첫 줄에
   `건물 밖에서 88m · 남서쪽 출입구 (B1F)(으)로 진입` 으로 나온다.

### 실외 구간은 건물을 돌아간다

처음엔 직선거리였다. 그러면 선이 건물을 뚫는다 - 표본의 55%가 그랬고 최악은
98m 중 60m 였다. "건물 밖에서 155m" 라고 안내하면서 건물을 가로지르는 선을
그리는 건 거짓말이다.

그래서 건물을 장애물로 두고 둘레를 도는 가시성 그래프를 쓴다(`fp/outdoor.py`).
실내 길찾기와 같은 원리인데 폴리곤 안이 아니라 밖을 돈다. 꺾이는 곳은
장애물의 볼록한 모서리뿐이다. 정적인 부분(모서리 36개 · 변 96개)은 빌드할 때
만들어 번들에 싣고(2KB), 사용자가 찍은 점에서 뻗는 변만 실행 시간에 잇는다.

세 가지가 함정이었고 셋 다 측정해서 찾았다:

| 함정 | 증상 | 해결 |
|---|---|---|
| 볼록/오목 판정 뒤집힘 | 날개 끝 대신 안쪽 홈만 노드로 잡아 변이 105쌍 중 5개 | 부호 대신 "이웃을 잇는 현이 건물 살을 지나는가" 로 판정 |
| 전 층을 합친 실루엣 | 위층 처마 때문에 B1F 출입구가 안쪽 13.5m 에 파묻힘 | 지면에 닿는 층(B1F·1F)만 씀. 보행자를 막는 건 1층 벽이다 |
| 방 박스가 서로 안 닿음 | 46조각으로 흩어져 그 틈으로 길이 남 | 0.3m 닫힘 연산으로 틈을 메워 한 덩어리로 |

위경도 좌표로 기하 판정을 하면 안 된다. `orientation()` 의 여유가 1e-7 인데
위경도에서 50m 선분 두 개의 외적이 2e-7 언저리라 진짜 교차를 삼킨다. 실외
기하는 미터로 펴서 다룬다.

결과: 관통 **0/288건** · 직선보다 짧아진 경우 0건 · 우회 중앙값 1.02배 ·
실외 구간 평균 1.8회 꺾임.

### 실외 구간은 지도의 보행자 길찾기를 쓴다

건물만 피해 도는 것으로는 부족하다. 도로도 옆 건물도 모르니 잔디밭을
가로질러 거의 직선으로 간다. 지도는 이미 TMAP 보행자 경로(실패 시 OSRM)를
쓰고 있으니 실외 구간도 그걸 쓴다.

엔진은 비동기 호출을 하지 않는다. 밖에서 재 온 결과만 받는다:

```js
engine.route({outdoor: true, lat, lng}, dest, {approaches: {노드: {meters, path}}})
```

호출 한도가 분당 30회라 출입구 11개를 다 잴 수는 없다. `entranceCandidates`
가 건물만 피한 어림값으로 총 소요를 계산해 **상위 3개**만 추리고(8ms),
그 셋만 실제로 잰다. 재 보지 않은 문은 후보에서 뺀다 — 어림값과 실측값을
섞어 비교하면 안 잰 문이 부당하게 짧아 보여서 그리로 가 버린다.

먼저 어림값으로 즉시 그리고, 실측이 오면 갈아 끼운다. 기다리는 동안 화면이
비어 있으면 눌러도 반응 없는 것처럼 보인다. 늦게 온 실측이 새 경로를 덮지
않도록 토큰으로 막는다.

API 가 죽으면 어림값이 그대로 남는다(`outdoor_measured: false`). 길이 아예
안 나는 것보다 낫다.

`PROXY_URL` 은 본서버(3000)에서 **일부러 빈 문자열**이다(같은 출처 상대경로).
`!window.PROXY_URL` 로 막으면 정작 본서버에서만 안 돈다.

건물만 피하는 그래프는 그대로 남아 두 가지 일을 한다. 후보를 추리는 어림값이고,
API 가 죽었을 때의 대비책이다.

### 왜 "가장 가까운 문" 이면 안 되는가

처음엔 가장 가까운 출입구를 골라 거기서 출발시켰다. 출입구가 한둘일 땐
차이가 없다. 실제로 11개(B1F 4 · 1F 7)가 그려지자 무너졌다.

바깥 지점 × 목적지 표본에서 **가까운 문 선택이 67% 에서 손해**였고,
중앙값 34초 · **최악 130초** 였다. 경사지라 B1F 문과 1F 문이 1.6m 간격으로
겹쳐 있어서, 코앞의 문이 지하 복도로만 이어지면 12m 더 걸어 다른 문으로
들어가는 편이 2분 빨랐다.

거리로 문을 고르는 것 자체가 틀렸다. 고를 기준은 **도착까지 걸리는 시간**이고,
그건 탐색을 돌려 봐야 안다. 그래서 문을 고르지 않고 전부 깐다. 탐색은
여전히 한 번만 돈다.

### 출입구 이름

`room_id` 를 비우면 건물 중심 기준 방위로 자동 명명한다
(`서쪽 출입구 (1F)`, 같은 방위·같은 층에 여럿이면 `남쪽 출입구 1 (B1F)`).
`출입구 7` 같은 번호는 밖에 서 있는 사람에게 아무 정보도 주지 않는다.

기준점은 **복도 노드 외접 상자의 중심**이지 출입구들의 평균이 아니다.
평균을 쓰면 문이 한쪽 면에 몰렸을 때 기준점이 그 면으로 끌려가서 나란히 붙은
두 문이 "북쪽" 과 "남쪽" 으로 갈린다. 도면에 이름을 적어 두면 그게 이긴다.

### 확인한 것

`tests/test_exterior_doors.py` (16건) 이 그래프 계약과 이름 규칙을,
`tests/exterior_route_check.py` 가 브라우저 엔진까지 끝단을 확인한다.

문 선택이 정말 최적인지는 믿을 게 아니라 세어 봐야 한다. 그래서 출입구를
하나만 남긴 엔진으로 **전수 비교**한다 — 바깥 12지점 + 각 문 앞 11지점 ×
목적지 24개 = **552건에서 어긋남 0건**. 구간 합과 총계도 552건 모두 일치한다
(실외 구간을 두 번 세지 않는다). 옛 방식 대비 중앙값 13초 · 최대 113초 단축.

`tests/browser_outdoor_playback_check.py` 는 실외 구간 재생을 본다. 실외
구간은 도면 픽셀이 없어서 재생 타임라인이 계단으로 오인하기 쉬웠고, 실제로
그랬다.
