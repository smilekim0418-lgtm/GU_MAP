# 테크노관 공식 DWG 실내지도

학교에서 제공한 `GIS_DATA/001.테크노관.dwg`로 B1F~6F의 CAD 벡터 지도를 만들었다. 기존 이미지 기반 지도, 방 폴리곤, IMDF, 길찾기는 유지된다.

## 열기

프로젝트 루트의 **`테크노관-CAD.html`을 더블클릭**한다. 인터넷이나 별도 서버가 필요 없다. 실행 중인 GUMAP에서는 테크노관 실내지도 패널의 **학교 공식 CAD 지도 보기**를 누르면 현재 층으로 열린다.

- 층 전환, 전 층 호실·실명 검색, 확대·이동
- CAD 벽선, 문 개폐호, 계단, 승강기와 가구 등 원본 선형
- 두 점 사이의 CAD 거리 측정(m)
- 자동 공간 구획과 원본 CAD 선형의 중첩 표시
- 기존 이미지 기반 경계의 비교 표시
- 현재 층 SVG 및 자동 구획 GeoJSON 다운로드

## 계단·엘리베이터 표시 추가

7개 층에 시설 위치 마커를 추가했다. 계단은 주황색 계단 아이콘, 엘리베이터는 보라색 승강기 아이콘이다. 기본으로 표시되며 체크박스로 숨길 수 있다. 층별 이동시설 버튼, `계단`·`엘리베이터`·`승강기`·`EV-1` 검색, 지도 아이콘 클릭으로 해당 시설을 선택한다. SVG에도 아이콘과 이름이 포함되고, 화면의 공간·시설 GeoJSON 저장은 Polygon과 시설 Point를 함께 내보낸다.

| 층 | 계단 표시 | 엘리베이터 표시 |
|---|---:|---:|
| B1F | 3 | 3 |
| 1F | 6 | 3 |
| 2F | 7 | 3 |
| 3F | 6 | 3 |
| 4F | 6 | 3 |
| 5F | 5 | 3 |
| 6F | 4 | 2 |
| 층별 합계 | 37 | 20 |

이는 층별 마커 수이며, 건물의 독립된 계단실·승강기 대수가 아니다. 기존 시설 53개 위치를 각 층 CAD 형상과 대조했고, CAD에서 확인한 2F 동측 외부계단, 5F 계단-E 옥상부, 6F 계단-C/F 옥상부를 추가했다. 추가 표시는 연결층이나 통행 가능 여부를 새로 확정하지 않는다. 하부층·옥상 윤곽에 보이는 모든 선을 해당 층의 이동시설로 간주하지 않았다.

`facilities.json`에 원본 DWG 해시, 층별 로컬 좌표, 대조 방법을 저장한다. `output/*.facilities.local.geojson`은 이름·종류·실내/외부/옥상부 구분·근처 CAD handle을 포함한다. 시설은 **위치 Point**이며 외곽 다각형이나 문 위치를 의미하지 않는다. `routing_verified=false`로 보관하며 기존 길찾기 그래프는 수정하지 않았다. `review_facilities.py`의 대조 그림은 `output/facility-review-*.png`에 있다.

브라우저 검사에 시설 누락·중복, 20개 엘리베이터 검색, 층간 시설 검색, 지도 아이콘 클릭, 표시 전환, SVG/GeoJSON 시설 포함 여부를 추가해 통과했다.

호실 수는 **DWG의 중복 없는 번호 텍스트 수**이며 현재 운영 중인 방의 총수나 공간 분할 정확도가 아니다. 단일 호실 구획 후보 역시 정확도 평가 결과가 아니다.

`output/index.html`은 데이터가 포함된 독립 실행 지도다. `output/map.json`은 모든 층과 비교 정보를 담는다. 층마다 `*.linework.local.geojson`, `*.labels.local.geojson`, `*.spaces.local.geojson`, `*.doors.json`을 생성한다. **모든 local 파일은 CAD 로컬 미터 좌표이며 WGS84 GeoJSON이 아니다.** `origin_dwg_mm + local_m * 1000`으로 DWG 좌표에 되돌아갈 수 있다. Y축은 위로 증가한다.

`output/quality_report.json`은 누락·신규 호실과 구획 검토 항목, `output/verification.json`은 코드·브라우저 검사 결과, `output/preview*.png`는 실제 화면이다.

## 처리 방법

1. DWG의 AC1024(AutoCAD 2010), `INSUNITS=4`(mm), 7개 평면도 제목을 확인했다.
2. [LibreDWG 공식 배포본 0.14](https://github.com/LibreDWG/libredwg/releases/tag/0.14)의 `dwg2dxf`로 로컬 DXF 변환 후 ezdxf로 읽었다. 설치되어 있던 TrueView Core Console은 DXF 내보내기 명령을 지원하지 않아 사용하지 않았다.
3. INSERT 블록의 변환을 적용하고 LINE·ARC·CIRCLE·POLYLINE·SPLINE 등을 추출했다. 원본 handle과 layer를 보존한다. 곡선은 2 mm 기준으로 분할하며 직선은 원래 끝점을 사용한다.
4. 각 층 제목 주변의 평면도 영역을 잘라 로컬 미터로 변환했다. 치수 레이어와 제목을 제외하지만 구조 레이어에 섞인 치수선 일부는 남을 수 있다. 이 선형은 전부 벽이라는 의미가 아니며 문·가구·기구도 포함한다.
5. 자동 구획은 선 교차점 1 mm 정밀도, 문 원호 반지름 선, 최대 40 mm 제도 틈 연결을 사용했다. 이 보정은 **구획 후보에만** 적용되며 원본 선형은 수정하지 않는다. 후보 경계는 벽면의 자동 재구성 결과이고 문턱의 폭·통행 여부를 확정하지 않는다.
6. 실명은 OCR 없이 CAD TEXT/MTEXT에서 읽었다. 화장실·샤워실 번호는 외부 라벨일 수 있어 자동 공간 배정에서 제외했다. 예를 들어 2F 208호 번호가 놓인 중정을 208호 화장실로 색칠하지 않는다.
7. 기존 방보다 면적이 현저히 작은 후보는 `partial_room_candidate`로 표시했다. 예: 2F 201 계단식 강의실의 단차선으로 분리된 부분. 단일 라벨이 포함돼도 전체 방 경계라고 확정하지 않는다.

## 아직 확정하지 않은 사항

- 화장실·샤워실의 외부 라벨 연결, 무명 공간의 복도·계단·승강기 용도 분류, 일부 강의실 내부 단차선의 합치기, 다수 호실을 포함하는 구획은 검토가 필요하다. 293개 후보를 완성된 방 293개로 간주하면 안 된다.
- 문 원호 834개는 문짝 기호 **후보**다. 양개문 중복, 연결 공간, 실제 출입 가능 여부와 층간 연결은 확정하지 않았다. CAD를 근거로 새 길찾기 그래프를 배포하지 않았다.
- 기존 경계 비교는 공통 호실 중심과 CAD 라벨을 기준으로 한 **평행이동만** 적용한다. 각 층 라벨 대응 편차 중앙값은 약 0.2~0.7 m다. 라벨 위치와 방 중심은 다르므로 정합 정확도 지표가 아니다. CAD 자체를 늘리거나 기존 지리좌표를 바꾸지 않았다.
- 2F `221-1`, 3F `301-1/2/3`, B1F `B133` 등 새 호실과 이전 도면의 차이는 보고서에 기록했다. 최신 실 사용 현황은 DWG의 작성·수정 시점과 별도 확인해야 한다.
- 변환 로그에 `SORTENTSTABLE`, `DICTIONARY`, 두 `ACAD_PROXY_ENTITY` 오류와 특수 객체 경고가 있다. HATCH 5개, DIMENSION 85개, IMAGE 1개는 추출 단계에서 제외했다. 선·문자 지도는 확인했지만 **DWG의 모든 특수 객체까지 무손실 변환했다고 보장하지 않는다.** 원본과 `source/conversion.log`를 함께 보관한다.

## 다시 만들기

Python 3.13 환경에서 실행했다. 아래 명령은 프로젝트 루트 기준이다.

```powershell
$env:PYTHONUTF8 = '1'
python -m pip install -r GUMAP-개발/floorplan/cad/requirements.txt
python GUMAP-개발/floorplan/cad/preserve_legacy.py
python GUMAP-개발/floorplan/cad/convert.py
python GUMAP-개발/floorplan/cad/extract_vectors.py
python GUMAP-개발/floorplan/cad/build.py
python GUMAP-개발/floorplan/cad/verify.py
```

변환기 기본 위치는 `source/libredwg/dwg2dxf.exe`다. 다른 위치라면 `convert.py --converter <경로>`를 사용한다. 도구/DXF 캐시는 `source/`에 있으며 Git에서 제외된다. 다른 PC의 브라우저 검사에는 `python -m playwright install chromium`이 필요할 수 있다. 뷰어만 사용한다면 Python이나 CAD 변환기가 필요 없다.

구획이나 화면만 수정할 때는 `build.py`부터 실행한다. DWG 해시가 바뀌면 캐시 사용을 거부하므로 먼저 재변환·재추출해야 한다. `preserve_legacy.py`는 기존 스냅샷을 덮어쓰지 않는다.

브라우저 검사는 7개 층 전환, 층간 검색, 비교 표시, 10 m 거리 측정, SVG/GeoJSON 다운로드, 화면 크기 변경, 루트 진입 페이지, 메인 지도 진입 버튼의 층 전달을 검사했다. 생성 구획 유효성·호실 중복과 원본/백업 해시도 검사했다. 독립적인 현장 실측 정확도나 길찾기 검증을 대신하지 않는다.

## 외부로 통하는 문 찾기와 메인 GUMAP 연동

세 가지를 더 했다. 기존 이미지 기반 실내지도 전체 백업, CAD 에서 외부 출입문 찾기, 그리고 메인 GUMAP 지도에 CAD 레이어 얹기다. 기존 IMDF 방 폴리곤·호실 정보·길찾기 그래프는 그대로다.

### 1. 기존 실내지도 백업

```powershell
python GUMAP-개발/floorplan/cad/backup_legacy_indoor.py
python GUMAP-개발/floorplan/cad/restore_legacy_indoor.py            # 미리보기
python GUMAP-개발/floorplan/cad/restore_legacy_indoor.py --write    # 실제로 되돌리기
```

`backup/실내지도-도면기반-<날짜>/` 에 74개 파일 30.7 MB 를 뜬다. 층별 폴리곤·라벨·래스터, 좌표 변환, IMDF 8종, 프론트 실내지도·길찾기 번들, 진입 HTML 3개가 들어간다. `manifest.json` 에 파일마다 SHA-256 과 바이트 수가 있고, 복구는 복사 후 해시를 다시 확인한다. 이미 있는 백업 폴더는 덮어쓰지 않는다.

`cad/legacy_snapshot/` 과 목적이 다르다. 그쪽은 "CAD 작업이 기존 파일을 안 건드렸다" 를 증명하는 24개 핵심 파일이고, 이쪽은 실제로 되돌릴 수 있는 복구본이다. 백업 폴더는 `.gitignore` 에 넣었다. 안에 든 tracked 파일은 이미 git 이력에 있고 나머지 28 MB 는 래스터 중간 산출물이다.

### 2. 외부로 통하는 문 (CAD 단독 판정)

```powershell
python GUMAP-개발/floorplan/cad/exterior_doors.py
python GUMAP-개발/floorplan/cad/review_entrances.py   # 층별 대조 그림
```

**기존 이미지 기반 지도의 '외부' 표기는 판정에 쓰지 않는다.** 전부 DWG 에서만 나온다. 기준은 하나다: 그 문이 그 층 건물 외피를 가로지르는가.

외피는 이렇게 만든다. CAD 벽선을 1.2 m 굵혀 한 덩어리로 붙이고, 구멍을 메우고, 굵힌 만큼 되깎는다. 그 다음 **이 층에 실제로 쓰는 범위**로 자른다. 그 범위는 호실 번호가 찍힌 구획과, 그 사이를 잇는 가늘고 긴 구획(면적/둘레 < 1.5 m, 면적 ≥ 15 m²)이다. 5·6층 도면에는 아래층 지붕 윤곽이 같이 그려져 있어 이 자르기가 없으면 지붕까지 건물로 잡는다. 지붕 타일 해치로 생긴 잔 구획은 면적으로 걸러 낸다. 외피는 `output/*.envelope.local.geojson` 에 폴리곤으로 저장한다.

문짝은 여닫이 원호(90°)와 양방향 자재문(180°)을 함께 읽는다. `build.py` 는 90° 만 봐서 1층 동서 연결통로의 양개 자재문 같은 180° 원호를 통째로 놓치고 있었다. 경첩에서 어느 쪽이 문틀인지는 **원호 끝점 중 벽에 닿는 쪽**으로 정한다. '주변에서 가장 평행한 벽' 으로 고르면 문 옆 직각 칸막이에 끌려간다.

| 층 | 문짝 원호 | 외부 | 중정 | 트인 곳 | 막힌 후보 | 문짝 없는 개구부 | 외피 m² |
|---|---:|---:|---:|---:|---:|---:|---:|
| B1F | 97 | 11 | 0 | 6 | 5 | 20 | 2,965 |
| 1F | 176 | 23 | 0 | 8 | 15 | 20 | 4,459 |
| 2F | 164 | 9 | 3 | 1 | 11 | 21 | 4,719 |
| 3F | 155 | 5 | 0 | 0 | 5 | 16 | 5,349 |
| 4F | 152 | 6 | 0 | 0 | 6 | 16 | 5,179 |
| 5F | 68 | 2 | 1 | 0 | 3 | 17 | 3,685 |
| 6F | 38 | 5 | 0 | 0 | 5 | 27 | 2,620 |
| 합계 | 850 | 61 | 4 | **15** | 50 | 137 | |

외피를 넘는 문 65개를, **나가서 얼마나 트여 있는지**로 두 등급으로 가른다. 문턱에서 바깥쪽으로 직진해 벽에 막히기까지의 거리가 4 m 이상이면 `트인 곳`, 아니면 `막힌 후보` 다. 건물 외벽의 출입문은 바로 앞이 마당이라 멀리 트여 있고, 계단실이나 발코니로 나가는 문은 몇 m 앞에서 막힌다. 외피 판정만으로는 이 둘을 못 가른다. 계단실을 이 층 범위에 넣으면 이번에는 진짜 외벽 문을 놓치기 때문에, 가르지 않고 등급으로 남긴다. 지도는 `트인 곳` 15개를 기본으로 보여주고 나머지 50개는 체크박스 뒤에 둔다.

문짝이 아예 없는 개구부 137개는 **지도에 올리지 않는다.** 외피 경계에서 벽선이 끊긴 자리라 진짜 개방 출입구일 수도, 중정을 면한 외피 경계일 수도 있다. `output/*.entrances.local.geojson` 에 `certainty=review` 로 남겨 둔다.

**기존 지도와의 대조.** 이전 이미지 기반 지도에는 사람이 손으로 찍은 '외부' 문이 B1F 4개, 1F 7개, 합 11개 있었다. CAD 단독 판정이 그중 **9개를 3 m 안에서 되짚었다**(B1F 3/4, 1F 6/7). 못 되짚은 둘은 B1F `(-43.8, 55.7)` 과 1F `(43.9, 91.5)` 로, 둘 다 옥외 계단참으로 나가는 문이다. 평면도 벽선만으로는 그 계단참에 지붕이 있는지 없는지를 알 수 없어 외피가 실내로 잡는다. 이 수치는 `output/entrances_report.json` 의 `legacy_reproduced` 와 `legacy_missed` 에 기록하고 테스트가 지켜본다(9개 밑으로 떨어지면 외피 쪽이 깨진 것이다). **판정에는 쓰지 않는다.**

확정하지 않은 것: 자동문·미닫이처럼 원호가 없는 출입구는 문짝 원호로 찾지 못한다. 잠긴 문, 관리자 전용문, 비상구도 구분하지 않는다. 통행 가능 여부는 전혀 확정하지 않았고 `routing_verified=false` 로 둔다. `output/entrance-review-*.png` 가 층별 대조 그림이다. 초록이 외피, 빨강이 외부 판정 문, 주황이 개방 개구부, 노란 별이 기존 지도의 '외부' 표기다.

| 층 | 호실 번호 | 경계 있음 | 번호만 | 방 밖에 적힌 표기 |
|---|---:|---:|---:|---:|
| B1F | 35 | 30 | 2 | 3 |
| 1F | 60 | 52 | 0 | 8 |
| 2F | 71 | 64 | 1 | 6 |
| 3F | 77 | 69 | 2 | 6 |
| 4F | 72 | 64 | 1 | 7 |
| 5F | 28 | 24 | 1 | 3 |
| 6F | 10 | 8 | 0 | 2 |
| 합계 | 353 | 311 | 7 | 35 |

경계는 `build.py` 가 벽선에서 만든 구획 후보다. **실측 방 경계가 아니다.** 번호 하나가 깔끔히 들어앉은 311개는 남색 실선, 한 구획에 번호가 여럿이거나 방이 잘린 것은 주황 점선으로 구분해 그린다.

방 밖에 적힌 표기 35개는 지도에 올리지 않는다. 도면이 화장실·계단 옆 호실 번호를 방 밖으로 빼서 인출선으로 잇는데(층마다 되풀이되는 `228`·`229`, `327`·`328`, `428`·`429` 와 1층 `155`·`138`·`139` 같은 것들), 글자 자리에 그대로 찍으면 건물 밖에 번호가 떠 버린다. 어느 방을 가리키는지는 확정하지 않았다. 빠진 번호는 `index.json` 의 `labels_outside_building` 에 층별로 적어 두고, 기존 IMDF 실내지도에는 그대로 나온다.

### 4. 메인 GUMAP 연동

```powershell
python GUMAP-개발/floorplan/cad/publish.py            # 미리보기
python GUMAP-개발/floorplan/cad/publish.py --write    # 실제로 내보내기
python GUMAP-개발/floorplan/cad/browser_cad_layer_check.py
```

`GUMAP-학교지도/data/cad/{층}.json` 에 층별 선형·호실·외곽선을, `index.json` 과 프론트 번들 `map-techno-cad-data.js` 에 층 목록·좌표 변환·출입문을 쓴다. 좌표는 cm 정수라 층당 0.11~0.38 MB 이고, 그 층을 처음 볼 때만 받아 온다.

`map-techno-cad-layer.js` 가 테크노관 실내지도 패널에 **학교 공식 CAD 도면** 칸을 만든다.

| 항목 | 기본 | 내용 |
|---|---|---|
| CAD 벽·문 선형 | 켬 | DWG 원본 선형과 이 층 건물 외곽선 |
| CAD 호실 경계·번호 | 켬 | 구획 경계는 항상, 번호는 줌 19 이상에서 |
| 외부 출입문 | 켬 | 트인 곳 15개 |
| 막힌 출입문 후보까지 | 끔 | 나머지 50개 |

선형은 층마다 1만 개가 넘어 `L.Polyline` 으로 올리면 층 전환 때 화면이 멎으므로 캔버스 한 장에 직접 그린다. 점은 줌 20 기준으로 한 번만 투영해 두고 그릴 때는 배율·평행이동만 건다.

좌표는 CAD 로컬 미터 → (기존 지도와 같은) 도면 로컬 미터 → WGS84 로 간다. 가운데 단계는 층마다 구한 **평행이동 하나뿐**이다. CAD 축척도 회전도 건드리지 않고 기존 좌표 변환도 고치지 않는다. 두 지도가 같은 자리에 겹쳐야 비교가 되기 때문에 일부러 기존 변환에 맞췄다.

평행이동은 같은 호실의 **방 중심끼리** 맞춘다. 축마다 중앙값을 쓰고(3층처럼 번호가 엉뚱한 방에 붙은 짝이 섞여 있어 평균은 못 쓴다), 잔차 중앙값은 층별 2~11 cm 다.

| 층 | B1F | 1F | 2F | 3F | 4F | 5F | 6F |
|---|---:|---:|---:|---:|---:|---:|---:|
| 대응 방 | 25 | 51 | 63 | 61 | 62 | 22 | 7 |
| 잔차 중앙값 (m) | 0.057 | 0.025 | 0.038 | 0.057 | 0.057 | 0.047 | 0.110 |

`build.py` 도 평행이동을 하나 구해 두지만 그건 **CAD 번호 글자 위치**와 **기존 방 중심**을 맞춘 값이라 쓰지 않는다. 도면은 호실 번호를 방 한가운데가 아니라 아래쪽에 적는 일이 많고, 그 치우침이 통째로 평행이동에 섞인다. 처음에는 그 값을 그대로 썼는데 일곱 층 **전부가 똑같이 북쪽 0.57 m · 서쪽 0.2 m** 밀렸다. 지도에서 CAD 벽선이 기존 방 색칠에서 한 칸 비켜 보였다. 잔차 중앙값만 보면 안 드러나고 편의(bias)를 따로 재야 보인다. 지금은 CAD 구획 중심과 기존 IMDF 방 중심의 거리가 층별 중앙값 0.02~0.11 m, 동서·남북 편의가 0.02 m 이하다.

바꾼 기존 파일은 `index.html` 과 `GUMAP-일반지도/index.html` 의 script 태그 두 줄씩이 전부다. IMDF 번들, 길찾기 그래프, 방 폴리곤, `techno_georef.json` 은 건드리지 않았다. 레이어를 끄면 예전 화면 그대로다.

브라우저 검사(`browser_cad_layer_check.py`)는 정적 서버에 실제 `index.html` 을 띄워 1층 선형이 캔버스에 그려지는지, 확대하면 호실 번호가 늘어나고 호실 표시를 끄면 줄어드는지, 출입문 마커가 트인 곳 8개에서 후보 포함 23개로 늘어나는지, B1F 로 바꾸면 그 층을 받아 다시 그리는지, 끄면 캔버스와 마커가 빠지고 기존 실내지도는 남는지를 본다. 화면은 `output/cad-layer-*.png` 에 있다.

`tests/test_cad_entrances.py` 는 출입문마다 근거가 되는 CAD 원호 handle 이 있는지(기존 지도에서 흘러든 항목이 없는지), 등급이 실제 개방폭과 맞는지, 검토 등급이 지도에 나가지 않는지, 호실 번호 353개가 지도에 오르거나 못 올린 이유가 적히거나 둘 중 하나인지, 좌표 변환의 축척이 1.0 이고 두 축이 직교하는지, 백업이 원본과 같은 해시인지를 검사한다. 기존 지도 재현 9/11 도 함께 지켜본다.

### 5. 실내 로드뷰 프로토타입

```powershell
python GUMAP-개발/floorplan/cad/panorama_nodes.py          # 촬영 계획 + 뷰어 생성
python GUMAP-개발/floorplan/cad/browser_panorama_check.py  # 뷰어 브라우저 검사
python GUMAP-개발/floorplan/cad/browser_cad_layer_check.py # 지도 연동까지 같이
```

메인 지도에서 테크노관을 **줌 19 이상으로 확대**하면 복도에 촬영 지점이 점으로 찍힌다. 점을 누르면 **작은 창**이 뜨고, 거기서 `⛶ 전체화면`을 눌러야 비로소 화면 전체로 넓어진다. 지도를 보다가 안이 궁금할 때 지도를 잃지 않게 하려는 것이다. 전체 화면으로 따로 보려면 루트의 **`테크노관-360투어.html`** 을 열거나 실내지도 패널의 **실내 360 투어 열기**를 누른다.

**아직 카메라가 없어 실사진이 하나도 없다.** 그래서 파노라마를 CAD 벽선에서 실시간으로 합성해 넣는다. 사진처럼 보이려는 게 아니라, 사진이 들어올 자리에 무엇이 들어가고 **방위가 맞는지**를 지금 확인하려는 것이다. 화면에도 `프로토타입`이라고 붙여 두었다.

#### 로드뷰지 VR 이 아니다

카카오맵·네이버지도의 로드뷰와 같은 방식이다. 자유롭게 걸어다니는 화면이 아니라 **찍어 둔 자리들 사이를 건너뛰는** 화면이다. 그 사이는 보간하지 않는다. 사진이 없는 자리에는 갈 수 없다.

- 바닥에 촬영 지점을 잇는 **길**이 깔리고 진행 방향으로 갈매기표가 찍힌다. 복도 끝까지 이어져 보이도록 같은 방향으로 최대 여섯 칸 앞까지 뻗는다.
- 길 위 어디든 누르면 그 자리로 간다. 멀리 누르면 멀리 간다.
- `↑` `↓` 앞뒤로 한 칸, `←` `→` 둘러보기. 한 칸 나아가면 가던 쪽을 계속 보게 고개를 돌려 준다.
- 왼쪽 아래 미니맵에 도면·지점·연결·**현재 시야 부채꼴**·정북 화살표. 미니맵을 누르면 걸어서 못 가는 구역으로도 건너뛴다.

#### 촬영 계획 — 복도·계단·로비만

**호실 안에는 지점을 놓지 않는다.** 남의 연구실과 강의실 안을 360 으로 찍는 건 허락받을 일이 아니라 받지 못할 일이다. 그래서 복도 격자를 호실 폴리곤 **밖에만** 놓고, 문간은 **양쪽이 다 호실 밖일 때만** 남긴다. 복도와 복도를 가르는 방화문, 계단실 문, 건물 출입문이 여기 해당한다. 호실 문 앞도 뺐다 — 문이 열려 있는 동안 방 안이 그대로 360 에 들어오기 때문이다. 계단실과 로비는 호실 번호가 없어서 자연히 복도 격자에 들어온다.

| 층 | 지점 | 문간 | 복도·계단·로비 | 연결 | 구역 | 제일 큰 구역 |
|---|---:|---:|---:|---:|---:|---:|
| B1F | 149 | 19 | 130 | 249 | 6 | 50% |
| 1F | 188 | 50 | 138 | 407 | 4 | 66% |
| 2F | 172 | 35 | 137 | 288 | 6 | 89% |
| 3F | 185 | 36 | 149 | 257 | 14 | 51% |
| 4F | 145 | 27 | 118 | 206 | 10 | 45% |
| 5F | 94 | 22 | 72 | 150 | 9 | 36% |
| 6F | 70 | 10 | 60 | 143 | 5 | 40% |
| 합계 | 1,003 | 199 | 804 | 1,700 | | |

지점이 호실 안에 하나라도 들어가면 테스트가 잡는다(`inside_a_room == 0`). 계획을 들고 간 사람이 그 자리에 삼각대를 세우기 때문에, 규칙은 코드가 지켜야 한다.

연결은 **걸어서 닿는지**로 판정한다. 처음에는 두 지점을 잇는 직선이 벽을 지나는지만 봤는데, 복도 기둥 하나·문틀 하나에 걸려 끊겼다(1층 21%). 사람은 기둥을 돌아서 간다. 그래서 자유공간 격자 위에서 너비우선으로 퍼뜨려 9 m 안에 닿는 지점을 잇고, 돌아가는 길이 직선거리의 1.7배를 넘으면 버린다. 이 격자에서도 **호실을 뺀다.** 넣어 두면 두 복도가 연구실을 가로질러 이어진 것으로 나오는데, 그 길로는 촬영하며 지나갈 수 없다.

#### 한 층이 한 덩어리로 이어지지 않는다

제일 큰 구역이 층 지점의 36~89% 다. 호실을 빼고 복도로만 다니기로 하면서 숫자가 내려갔다. 예전 계획은 1층이 100% 였는데, **그건 연구실을 가로질러 이어진 것으로 세고 있었다.** 걸어서 찍을 수 있는 길이 아니었으니 그 100% 가 틀린 값이다.

1층 북쪽과 남쪽은 도면상 복도로는 이어지지 않는다. 사이에 있는 건 105호(테크노 관학사 지원실, 207 m²)다. 벽선 레이어를 하나씩 빼 가며 확인했고, 벽 여유를 0 으로 줄여도 이어지지 않는다. 래스터 여유 탓이 아니라 실제 벽이다. 3·4층은 복도 자유공간 자체가 110~130 m² 짜리 조각 여럿으로 끊겨 있는데, 그 자리에는 도면상 자동문·양개 자재문이 그려져 있다.

억지로 잇는 대신 **구역 번호**를 붙였다. 뷰어는 같은 구역 안에서만 바닥에 길을 깔고, 다른 구역은 미니맵에 흐리게 그린다. 흐린 점도 누르면 건너뛴다 — 걸어서는 못 가지만 지도에서는 갈 수 있다는 뜻이다. 실제 촬영에서는 밖으로 돌거나 다른 층을 거쳐 가면서 이어진다. 끊긴 구역 사이는 실제 도보 경로를 찾아 그 길 위에 지점을 더 놓는 보정을 한 번 돌리는데(`stitch_components`), 복도로 갈 길이 없으면 아무것도 하지 못한다. 테스트는 이 수치가 지금보다 나빠지지 않는지만 지켜본다.

도면 처리에서 하나 더 걸렸다. 도면은 **문짝을 닫힌 자리에 선 하나로** 그린다. 그 선을 벽으로 치면 모든 문간이 막힌다. 그래서 계획 단계에서는 문턱 가운데를 반지름 0.35 m 만큼 지워 문을 열어 둔다.

#### 지도 안 작은 창

`map-techno-pano-layer.js` 가 지도에, `panorama_viewer.html` 이 그 안에 들어간다. 창 안에 뜨는 건 같은 뷰어를 `?embed=1&floor=3F&node=17` 로 연 것이다. 지도 쪽 지점 번호와 뷰어 쪽 지점 번호가 같은 배열 순서라서 번호만 넘기면 그 자리가 열린다(테스트가 두 쪽 개수를 맞춰 본다). 창이 이미 떠 있으면 1.8 MB 를 다시 받지 않고 `postMessage` 로 번호만 보낸다.

#### 뷰어

`panorama_viewer.html` 이 틀이고, `panorama_nodes.py` 가 데이터를 박아 `output/panorama.html`(1.8 MB)을 만든다. 서버 없이 더블클릭으로 열린다.

등장방형 → 화면 변환은 three.js 셰이더로 직접 푼다. 구(sphere)에 텍스처를 씌우면 UV 규약을 눈으로 맞춰야 하는데, 그러면 "그럴듯해 보이는데 90도 돌아간" 상태를 못 잡는다. WebGL 이 없는 환경에서는 검은 화면 대신 왜 안 나오는지 적는다.

#### 방위 정합 검사

이 프로토타입에서 제일 중요한 건 **보는 방향이 도면 위 방위와 같은가** 다. 눈으로는 판별이 안 돼서 수치로 본다. 화면을 24방향으로 돌려 가며, 한가운데 픽셀 밝기와 **그 방향으로 CAD 에서 쏜 광선의 거리**를 맞춰 본다. 합성 화면은 거리에 따라 밝기가 정해지므로 둘이 일치해야 한다.

실제로 이 검사가 첫 구현의 오류를 잡았다. yaw ↔ 도면 각 변환을 반사(reflection)로 잘못 유도해서, 어떤 각도에서는 우연히 맞고 어떤 각도에서는 크게 어긋났다. 화면만 봐서는 "복도가 보이네" 하고 넘어갔을 것이다.

| 검사 | 결과 |
|---|---|
| 24방향 모두 보는 쪽 벽이 맞는다 | 밝기 차 중앙값 0 / 최대 1 |
| 정면에 둔 이웃의 **길 끝**이 화면 가운데 | 중심에서 0.0% |
| 바닥 길을 누르면 그리로 간다 | 91 → 43 |
| 방향키로 앞뒤로 오간다 | 43 → 45 → 43 (제자리 복귀) |
| B1F·6F 방위 | 밝기 차 최대 0 |
| 작은 창이 주소로 받은 자리에서 열린다 | 3F · 지점 17 |
| 작은 창 안에서 로드뷰가 실제로 돈다 | B1F · 길 4구간 |
| 전체화면을 누르면 그때 화면을 덮는다 | 1400×900 = 화면 전체 |

#### 실사진이 오면 바꿀 곳

한 군데다. `makeTexture()` 가 지금은 합성 캔버스를 돌려주는데, 그 자리에서 `node.photo` 의 등장방형 사진을 읽으면 된다. 사진마다 `node.yaw_offset`(정북 보정, 도)을 넣어 가로로 굴리면 나머지(미니맵 부채꼴, 바닥 길, 방위 표시)는 그대로 돈다.

정북 보정값은 손으로 넣어야 한다. **카메라 내장 나침반은 실내에서 못 믿는다** — 철골·배전반·엘리베이터 근처에서 수십 도씩 틀어진다. 촬영할 때 카메라 정면을 복도 진행 방향 같은 일정한 기준으로 두고, 나중에 CAD 벽 방향과 대조해 층마다 한 번씩 맞추는 편이 확실하다.

확정하지 않은 것: 이 지점들은 **촬영 계획**이지 촬영 결과가 아니다. 삼각대를 그 자리에 실제로 세울 수 있는지(가구·적재물·소화전), 그 복도에 들어가도 되는지, 찍은 사진에 사람이 찍혔는지는 전혀 확인하지 않았다. 1,000개를 다 찍는 것도 첫 촬영으로는 현실적이지 않다 — 주 출입구에서 계단·엘리베이터까지 이어지는 주 동선부터 찍는 게 맞다.
